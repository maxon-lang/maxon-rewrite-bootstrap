# The runtime

The runtime as Maxon source: one module, compiled with every program that `self/` builds. The design (how a compile
finds this directory, the `__Raw` intrinsics, how an entry the compiler calls maps to a function here, the globals) is
the root README's section "The runtime". `minimaxon check runtime` checks it, and `.\check.ps1` runs that.

| File | Entries the compiler calls | Holds |

| `heap.maxon` | `alloc`, `free` | a heap per thread: boxes in size classes carved from chunks of the process heap, a large box a block of its own (on Linux, freed ones kept by the freeing thread for reuse), the list of a heap's boxes that other threads freed, the count of live boxes summed over the heaps, and the blocks the runtime keeps for the life of the process |

## Rules a runtime file follows

- **Only the runtime calls `__Raw`.** Anywhere else a call of one is `E3152`.
- **An entry the compiler calls has the table's signature** (`runtimeFunctions` in `internal/builtingen/table.go`):
  words only (`Count`, `Byte`, `bool`, `String` as its box address), no `mutates`, no type parameter, no `throws`.
  `check runtime` refuses a missing one (`E3004`) and a different one (`E3005`). A new entry is a row of `entries` and
  of `runtimeFunctions`, then `go generate ./internal/...`, then its function here.
- **The same code for every build.** The runtime reads no build option: what an option changes is the entry stub's
  (`self/backend/entry.maxon`), as `--count-allocations` makes the stub call `checkLeaks`.
- **No primitives and no throwing.** The runtime implements `Array`, `Map` and the rest, so it uses none of them; a
  failure it cannot pass on is a `panic`, whose message is a literal, or `exitProcess`.
- **A layout is a named constant of `layout_gen.maxon`** (the table is `internal/abigen/table.go`), never a number in the code that reads the box.
- **Behaviour is maxon's runtime's**: the same messages, exit codes and Win32 calls, until a change is recorded in the
  root README's "Where it differs from Maxon".
- **A test of the runtime** is a program of `tests/runtime/`, which the test runner compiles as one more file of this
  module, so that it may call what no program can (root README, "Tests"). Its names start with `test` or `tally`, so
  as not to clash with the runtime's own.
- **One source, a branch per system.** An entry whose work is the system's is written once for each, in `#if os(Windows)` and
  `#if os(Linux)` (the Linux ones in the `linux` files), and an entry whose work is shared calls the system only in a branch of a
  statement; the target the compile is for picks the branch (root README, "Targets"). An entry that a system's branch lacks
  is refused by `check runtime --target=<arch>-<os>` (`E3004`), never a stub.
- **A system call is made by its number**, a named constant of `layout_gen.maxon` (`internal/abigen/linux.go`), with
  `__Raw.syscallN`; it gives `-errno` on a failure (`failed`, `errnoOf` of `linux.maxon`).
- **A DLL function is called by its name**, a string literal, which must be in the executable's import list
  (`importNames` in `internal/abigen/imports.go`, which generates `self/backend/imports_gen.maxon`); `self/backend` panics on one that is not.
- **A system call that may block is bracketed** by `enterBlocking` and `exitBlocking` (Go's entersyscall and exitsyscall),
  so that the monitor can hand the thread's processor to another thread meanwhile: file reads and writes, `write`, and the
  wait for a child. The bracket's exit may move the green thread to another thread, so a function that brackets a call
  holds nothing of the running thread (its context, its heap's record) across it. A panic writes with `writeHandle`, which
  brackets nothing, since it may come from code that holds the scheduler's lock.
- **Runtime code is never stopped by the monitor** (the link's table of preemptible code leaves it out), so an allocation,
  a queue operation or a lock's hold always ends on the thread it began on. The monitor allocates nothing and holds no
  processor.

## The scheduler and Go's

The scheduler is Go's (`runtime/proc.go`, Go 1.14 on for preemption), starting from maxon's runtime, which implements the
same design in its compiler (`maxon-bin/Compiler/Runtime/SchedRuntime.maxon`, `GtRuntime.maxon`, `NetpollRuntime.maxon`);
maxon's is code that emits IR, so it is the reference rather than a source `cmd/convert` takes. The names follow Go's:
`findRunnable`, `execute`, `runqPut`, `runqGet`, `runqSteal`, `globalGet`, `startThreadFor` (startm), `stopThread` (stopm),
`wakeProc` (wakep), `handOffProc` (handoffp), `retake`, `preemptOne`, `enterBlocking` and `exitBlocking`. A behaviour is a
green thread like any other: it is preempted after 10 ms and its processor is handed off in a blocking call, as a
goroutine's is. Where it differs from Go, and why:

- **Stacks never move.** A borrow is an address in a frame, so a stack cannot be copied to grow it as Go's is: each green
  thread's stack is a reserve of the main thread's size, `stackReserveBytes`, that the system commits a page at a time, its
  lowest page a guard, taken from a pool when the green thread first runs and given back when it finishes.
- **No stack maps, no garbage collector.** There is nothing to scan, so a stop needs no safe point beyond the code being
  the program's.
- **Preemption is asynchronous only.** maxon's guard-word checks in prologues are not ported, nor Go's cooperative
  stackguard requests: a green thread is stopped from outside (`SuspendThread` and `SetThreadContext` on Windows, SIGURG on
  Linux) in the program's code, never in the runtime's, a drop or copy routine, the stub or a DLL.
- **Park and ready carry a permit.** A ready that comes before its green thread has parked makes the next park return at
  once, where Go's gopark relies on the waker finding the waiter under a lock its unlockf releases: the runtime's waits
  (await, sleep, a poll descriptor) and a test's own then need no lock of their own.
- **Timers are one heap under the scheduler's lock**, as maxon keeps its timer store under `__sched_lock`, where Go 1.14
  keeps a heap per processor; the design's decision (`phase4/concurrency-design.md`, section 5).
- **`main` is a green thread, as Go's is a goroutine, in a program that uses the scheduler.** The stub calls `mainRun` with
  the code that calls `main`, which runs it on a green thread and the scheduler on the main thread until nothing is left.
  As Go's newproc wakes no thread before main has started, `main`'s green thread is queued on the main thread's processor
  with no thread woken for it (`queueReady`), so a program starts one thread of its own, the monitor's, until it makes work
  for more. A program whose code reaches no green thread is linked without any of this (root README, "Main with or without
  the scheduler"): `main` runs on the main thread, and the link puts routines that do nothing in place of `enterBlocking`,
  `exitBlocking` and `takeExitClaim`, and the stub's own in place of `osSetExitCode`, so the runtime's shared code never
  tests which kind of program it is in. Go has no such program; maxon's runtime starts its scheduler only for a program
  that uses it, as this does. `schedDrain` is called by no stub; it stays while the seed's table names it.
- **Records are made as they are needed**, as Go makes a P's caches lazily: a processor when a thread first takes it, a
  heap's chunks from 16 KB doubling to 1 MB, the blocks green threads' records are carved from from a page doubling to
  64 KB, and a green thread's stack committed a page at a time from one, so a program holds what it uses.
- **A behaviour takes its green thread when it starts.** A run queue's entry is a green thread or a runnable behaviour's
  record (tagged, linked through the word of its pending count in the global queue), and `execute` gives the behaviour
  a green thread from the processor's pool: Go makes a goroutine's g with it, but a behaviour is made by `when`, and a
  message waiting in maxon's cown queue holds no runner either, so a burst of runnable messages costs their records. The
  pools are bounded as Go's are: a processor keeps 64 records and 16 stacks and spills half to the scheduler's lists,
  which keep every record (Go never frees a g) and at most 64 stacks, a stack past that going back to the system as Go's
  collector frees the stacks of the global free list; a stack that committed more than 64 KB goes back when it is freed,
  as Go's gfput frees a stack not of the starting size (Windows only: Linux does not say how much was touched). A stack's
  record is at the top of its own reserve, so it goes back with it.
- **Strands are maxon's, which Go has not**: the coroutines of an async call run one at a time with the green thread that
  started them (`strand.maxon`), handing the strand over only where one waits, yields or finishes, as maxon's strand of a
  green thread does; a member that parks gives the strand up inside `park`, so every wait of the runtime is one of the
  strand's.
- **The heap stays the thread's (the M's), not the processor's.** A green thread allocates from the heap of the thread it
  runs on and may free on another, through the heap's list of boxes other threads freed. That is sound because runtime
  code is never stopped, so an allocation ends on the thread it began on. For the page heap to come, which shards by
  processor as Go's mcache does: a processor has one thread at a time (a thread takes one only from the idle list or by
  a hand-off, under the lock, or back from a blocking call by a compare-exchange the monitor's retake races), but a thread
  in a blocking call, one stopped with no processor, and the monitor hold none, and allocate (the monitor never does);
  the threads can outnumber the processors (a hand-off starts one); a thread's remote frees wait until it allocates again;
  and the leak check sums every thread's heap (`liveBoxes` walks `schedAllThreadsOffset`), which a per-processor heap must
  replace with a sum over the processors and the threads that hold none.
- **The monitor sleeps by `Sleep` on Windows**, whose resolution is the system timer's (often 15.6 ms), since the
  executable imports no high-resolution timer: a green thread runs 10 ms to about 30 ms before it is stopped there.
